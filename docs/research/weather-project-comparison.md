# 两份开源天气项目比较

研究日期：2026-10-14（Asia/Shanghai）。静态源码研究，未编译、未运行API、未烧录；建议不是已确认产品决策。

## 研究对象

1. https://github.com/dm5al/esp32-weather-station ，版本 `0e3debafc8b19757832f0b6b3756eea93585d73f`。详见[第一份研究](weather-station-assessment.md)。
2. https://github.com/johnsonfarmsus/lilygo-weather-station ，版本 `e03c7e39b6505c4abcf665b20a80660739557bea`。源码位于临时目录，仅作研究。

## 推荐结论

优先采用第一份的数据模块作为移植基础，保留本项目手表BSP、Wi-Fi、RTC、息屏和按键。第二份可参考三天预报的简洁展示思路，但不推荐复制其联网与更新主循环。两份都不能直接作为本手表固件烧录。

| 项目 | 第一份 | 第二份 |
|---|---|---|
| 框架 | ESP-IDF≥5.3、LVGL~9.2、C | Arduino/PlatformIO、LVGL8.3、C++ |
| 与本项目差异 | 同技术路线，仍需验证LVGL9.6兼容 | 网络、JSON库、LVGL接口及任务模型均需改造 |
| 目标硬件 | 微雪7英寸800×480 RGB屏 | LilyGo170×320 ST7789屏 |
| 天气服务 | Open-Meteo，一次请求获取多类天气 | OpenWeatherMap，当前天气及预报两次请求 |
| 城市 | 城市搜索/手动选择与IP定位 | Google Wi-Fi定位及固定经纬度回退 |
| 网络工作 | 独立任务，不阻塞LVGL | 同一loop内同步定位及HTTP请求，阻塞LVGL处理 |
| 请求防护 | HTTPS证书包、15秒超时、64KiB响应限制 | 天气URL为HTTP，源码未设显式超时/响应体上限 |
| 更新 | 15分钟更新、失败2分钟重试 | 30分钟更新；失败不推进lastUpdate，可能每轮loop再次请求 |
| 许可证 | 项目自有源码Unlicense | README声称MIT，但LICENSE正文为AGPLv3，需澄清 |

## 第二份具体发现

- `src/main.cpp:524`附近从预报列表第一项取温度，赋给`currentTemp`，并不是当前天气API温度。界面会把下一段3小时预报温度显示成当前温度。
- 今日高低温根据剩余预报时段聚合，不能视作完整当天的最高/最低温；代码还用上述预报温度补齐边界。
- `loop()`只在`weatherDataValid`为真时周期刷新，首次请求失败后没有看到自动恢复路径。已有数据更新失败时，`lastUpdate`不更新，超时条件持续成立，可能连续重复定位和天气请求。
- 数据过期红色星号在`updateWeatherDisplay()`内计算；该函数主要在请求成功后调用，成功又刚更新`lastUpdate`，因此旧数据经过两小时不会自动触发过期显示。
- 天气请求使用HTTP，API密钥置于URL。移植应改成带证书验证的HTTPS。
- README建议将`UNITS`改为metric，但界面温度单位仍硬编码为F，不能仅改配置就正确切换摄氏度。
- README描述每两小时定位，实际loop在每次天气更新前调用定位；不能仅依文档判断联网频率。
- 即使选择固定位置，配置校验仍要求Google定位密钥不是占位值，增加不必要的接入门槛。
- 代码集中在一个main.cpp，硬件驱动、UI、天气、定位混合；仓库test目录只发现说明文件，未发现实际测试。

上述为源码路径分析，未通过真机或故障注入实测。服务免费额度和收费按当前官方条款核验，不能直接沿用README中的历史数值。没有功耗实测，推荐依据为请求方式及移植成本，不能描述为续航对比结果。

## 第一份也需修复

关键字段缺失默认0、失败保留旧数据时提示不足、缓存提交不够原子，以及桌面设备刷新策略均需调整。第一份更合适不代表可以未经测试直接投入使用。

## 后续建议

先验证天气服务网络可达性，然后抽取第一份的HTTP/天气代码，强化字段校验与缓存，采用有界重试与按需刷新。天气页及城市设置按手表统一设计规范另行设计、验证。许可证与数据服务条款在真正移植前保留来源并再次核验。

本次仅研究并提出推荐，未新增功能、改变用户行为或确认产品决策，不新增产品记录编号。
