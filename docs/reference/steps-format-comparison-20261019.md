# 计步参数格式对照

2026-10-19。依据：QST 13-52-27 Rev A 第11章，及本地官方包SensorLib，commit b099739。只验证格式，不把假说当修复。

|编号|相对原版唯一变化|依据/疑点|
|---|---|---|
|0|原参数|对照基线，前轮30步/0|
|1|CAL4_H两组01/02→10/20，CAL4_L仍02|表38写(7:4)，正文与库写整个01/02，存在矛盾|
|2|CAL4_L两组02→00，组号仍01/02|表38标NA，清零仅为受控假说，不声称官方要求|
|3|第一组阈值C8/64→CC/66，其余原样|手册200mg/100mg示例使用u6.10编码CC/66|

每轮都从基线复制参数后只改表列因素，不将候选格式叠加；启停、ODR、滤波、供电/Wi-Fi与UI规则一致。命令STEPS_FORMAT1/2/3由传感器worker执行，先核对配置归属、停传感器，再下发/读回/握手/启用。STEPS_REINIT恢复0。

实验raw仅记录到串口，不加入日累计，所以实验期间不能用屏幕日步数判定成功，应比较日志与实际行走数。成功下发后120秒自动恢复基线；CPU重启也重新下发基线，避免IMU独立供电遗留试验配置。重配失败停止worker并释放AWAKE，需要重启恢复。试验参数不写NVS。

测试覆盖三格式字节、无效编号拒绝、实验raw不入日累计、120秒恢复、重启重配、读回错误与命令超时及原有存储/界面回归。构建、烧录、启动和运动验收分别记录。参数读回/握手通过不是算法内部接受或计步成功的证据。

## 实测结果

用户三轮分别报告30、30、30步。三格式的写入、逐字节读回和CTRL9完成/ACK均通过。完整启动捕获版本1.1.4、8MB PSRAM、显示及传感器初始化，无已发现panic/反复重启。

- 格式1：52份快照，raw均0，STATUS1均0，三轴明显运动。
- 格式2：49份快照，raw均0，STATUS1均0，三轴明显运动。
- 格式3：24份快照，raw均0，STATUS1均0，三轴明显运动；约启动281秒后串口中断，至用户回复的后段没有记录，不能声称第三轮全程完整。重新打开USB后通信恢复，不能将缺失区间当raw=0证据。

结论：在已采集的真实运动样本中，这三种单项参数格式改动均未产生步数；没有验证有效的格式修复。不证明所有参数组合无效，也不证明该芯片修订不支持计步。没有修改省电/供电路线。实验计数未写日累计。

私有证据：`firmware/backup/steps-format-20261019/serial.log`、`timeline.jsonl`、`analysis.json`、`user_results.json`、恢复确认日志。第三轮后段丢日志属于采集限制，下一轮连续采集需要保留有效USB连接状态并检测日志停更。

恢复确认：`restore-confirm.log`启动后429952ms记录格式0、两组原字节、0D/0D/0F握手及experimental=0。仅重新打开USB不被当成CPU重启证据，恢复由显式命令完成。
